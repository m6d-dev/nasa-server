# Vigil — ТЗ на сервер

Сопутствующие документы: `PLAN.md` (общий план, приоритеты), `DESIGN_TZ.md` (что показывает фронт).
Версия: 14.11.2026, ред. 2 (примеры приведены к порогам §7; добавлены приоритет состояний и правило для текстов).

---

## 1. Что делает сервер

Принимает кадры от устройств (виртуальное устройство и, если приедет, браслет), сворачивает их в минутные значения, определяет контекст (сон / покой / нагрузка), ведёт личную норму каждого человека, выставляет уровень состояния, называет тип отклонения, пишет к нему текст, собирает суточный отчёт и отдаёт всё это фронту по REST и WebSocket.

Один процесс, один event loop, состояние в памяти, Postgres — для минутных значений и событий. Никаких очередей, брокеров и воркеров.

### Уточнения к `PLAN.md`, принятые в этом ТЗ

| № | Было в плане | Стало | Почему |
|---|---|---|---|
| 1 | Один тип кадра (секундный) | Добавлен **тип 2 — минутный кадр** и бит «повтор истории» | 14 суток × 7 человек по секундам = 8,4 млн кадров; по минутам — 141 тыс. Догрузка истории за секунды возможна только так |
| 2 | Одна открытая тревога на причину | **Один открытый инцидент на человека** | проще серверу и фронту; экран Critical и Notices показывают один объект |
| 3 | Таблица `baseline_cell` | Таблицы нет; норма **восстанавливается из `agg_1m` при старте** | один источник правды, нечего синхронизировать |
| 4 | Жёсткий порог держится 60 с | Проверяется **на закрытии минуты** | вся логика на одном шаге; задержка ≤ 2 мин |
| 5 | Контекст «нагрузка» по расписанию или кнопке | **Бит 4 в `flags` кадра** — «идёт тренировка» | не нужен отдельный API и экран |

## 2. Границы

**Сервер делает:** приём, агрегацию, контекст, норму, уровни, инциденты, вызов модели XGBoost, тексты (шаблон + локальная LLM), отчёт, API.

**Сервер не делает:**

- не генерирует данные и сценарии — это виртуальное устройство (`vdev`, отдельный процесс);
- не обучает модели — получает готовые файлы от ML;
- не хранит секундные кадры в базе;
- нет авторизации пользователей; текущий человек задаётся параметром `crew` (по умолчанию 1);
- нет миграций: схема создаётся одним SQL-файлом при старте.

**Что сервер получает от других:**

| От кого | Что | Формат |
|---|---|---|
| EMB | кадры | §3 |
| EMB | управление симулятором | HTTP на `VDEV_URL`: `POST /scenario`, `/speed`, `/reset`, `GET /state` |
| ML | модель паттернов | `ml/models/pattern.json` (XGBoost) + `pattern_meta.json`: список признаков по порядку, список классов |
| ML | LLM | модель в Ollama под именем `vigil-narrator` |
| D2 | библиотека действий | `docs/actions.yaml`: паттерн × тяжесть → список ключей действий и их английский текст |
| EMB | радиация | `data/radlab/*.json` |

Если какого-то из файлов ML нет — сервер работает без него (§8.3, §9).

## 3. Кадр

Транспорт: WebSocket `/ingest`, бинарные сообщения, один кадр на сообщение. Одно соединение может нести кадры разных `dev_id`.

32 байта, little-endian, `struct.Struct("<BBHIHHHhHHHBBBBHhH")`:

| Смещ. | Тип | Поле | Единицы | «Нет данных» |
|---|---|---|---|---|
| 0 | u8 | `ver` | 1 | — |
| 1 | u8 | `type` | **1 — секунда, 2 — минута** | — |
| 2 | u16 | `dev_id` | | — |
| 4 | u32 | `ts` | unix-секунды UTC; для типа 2 — начало минуты | — |
| 8 | u16 | `hr_x10` | уд/мин × 10 | 0xFFFF |
| 10 | u16 | `spo2_x10` | % × 10 | 0xFFFF |
| 12 | u16 | `rr_x10` | вдохов/мин × 10 | 0xFFFF |
| 14 | i16 | `skin_t_x100` | °C × 100 | 0x7FFF |
| 16 | u16 | `co2_ppm` | ppm | 0xFFFF |
| 18 | u16 | `press_x10` | гПа × 10 | 0xFFFF |
| 20 | u16 | `act_mg` | милли-g | 0xFFFF |
| 22 | u8 | `sqi` | 0–100 | — |
| 23 | u8 | `flags` | см. ниже | — |
| 24 | u8 | `batt_pct` | % | 0xFF |
| 25 | u8 | `seq` | счётчик по кругу | — |
| 26 | u16 | `hrv_rmssd_ms` | мс | 0xFFFF |
| 28 | i16 | `amb_t_x100` | °C × 100 | 0x7FFF |
| 30 | u16 | `crc16` | CRC-16/CCITT-FALSE по байтам 0–29 | — |

`flags`: бит 0 — надет; бит 1 — зарядка; бит 2 — контакт ЭКГ; бит 3 — артефакт движения; **бит 4 — идёт тренировка**; **бит 7 — повтор истории** (без рассылки в `/live` и без вызова LLM).

Правила приёма:

- длина ≠ 32, `ver` ≠ 1 или CRC не сошёлся → кадр отброшен, счётчик `bad_frames` +1;
- неизвестный `dev_id` → отброшен;
- `ts` ≤ последнего принятого `ts` этого устройства → отброшен (дубликат или прошлое);
- разрыв в `seq` → счётчик потерь устройства.

## 4. Время

**Вся логика идёт по `ts` из кадра.** «Сейчас» для человека — `ts` его последнего кадра. Сутки — календарные сутки UTC по этому времени.

Часы сервера используются в одном месте: «сколько секунд назад пришёл последний кадр» (состояние связи на странице Device).

Каждый ответ API несёт `now_ts` — виртуальное «сейчас» этого человека. Фронт показывает время только из ответов сервера.

## 5. Конвейер

```
кадр ─► проверка ─► (тип 1) буфер секунд ─► закрытие минуты ─┐
                    (тип 2) ─────────────────────────────────┤
                                                             ▼
                       минута: значения ─► контекст ─► z по личной норме
                              ─► уровни ─► инцидент ─► паттерн ─► текст
                              ─► запись agg_1m ─► рассылка /live
```

Всё, что ниже закрытия минуты, выполняется синхронно в одном вызове `on_minute(crew, minute)`. Этот же вызов используется при восстановлении нормы из базы на старте (§6.6) и офлайн в ML — поэтому он живёт в `vigil/core/` и не знает ни про сеть, ни про базу.

### 5.1 Закрытие минуты (тип 1)

Минута закрывается, когда пришёл кадр из следующей минуты.

- Значение показателя = медиана по секундам с `sqi ≥ 50` и не «нет данных».
- Если таких секунд < 20 → показатель в этой минуте `null`.
- `act_mg`, `sqi` — среднее; `worn_frac` — доля секунд с битом «надет»; `valid_s` — число валидных секунд по пульсу.
- Пропущенные минуты в базу не пишутся. Отсутствие строки = нет данных.

### 5.2 Производные значения

`ppco2 [мм рт. ст.] = co2_ppm · 1e-6 · press_hpa · 0.750062`. Если давления нет — берётся 1013,25.

### 5.3 Контекст минуты

Проверяется сверху вниз:

| Код | Контекст | Условие |
|---|---|---|
| 0 | `off` | `worn_frac < 0.5` или `sqi < 20` |
| 3 | `active` | `act_mg ≥ 60` **или** бит «тренировка» в большинстве секунд; плюс 5 минут после окончания |
| 1 | `sleep` | `act_mg ≤ 8` не менее 15 минут подряд **и** пульс ≤ (медиана покоя или 60) + 5 |
| 2 | `rest` | остальное |

Пороги 60 и 8 — стартовые; ML уточнит по данным и пришлёт числа. Все константы — в одном файле `core/thresholds.py`.

## 6. Личная норма

### 6.1 Ячейка

Ключ: `(crew, metric, ctx, tod)`.

- `metric` ∈ `hr`, `spo2`, `rr`, `skin_t` (и `hrv`, если появится канал);
- `ctx` ∈ `sleep`, `rest`, `active`;
- `tod` = час UTC // 4 (0…5); для `active` — всегда 0.

В ячейке — кольцевой буфер минутных значений за последние 14 суток (до 3360 чисел) и множество дат, из которых они пришли.

### 6.2 Статистики

Пересчёт — раз в виртуальный час и при старте:

```
med = median(buf)
mad = median(|buf − med|)
sig = max(1.4826 · mad, SIGMA_FLOOR[metric])
lo, hi = med − 2·sig, med + 2·sig
```

`SIGMA_FLOOR`: hr 3.0 · spo2 1.0 · rr 1.5 · skin_t 0.3 · hrv 8.0.

Проверочный пример для теста: буфер `[56, 58, 57, 60, 55, 57, 59]` → med 57, mad 1, sig 3.0 (сработал пол), значение 66 → z = 3.0.

### 6.3 Готовность и откат

Ячейка **готова**, если в буфере ≥ 120 значений из ≥ 3 разных суток.

Какую норму брать для значения:

1. своя ячейка, если готова;
2. иначе ячейка того же контекста без учёта времени суток (объединение буферов), если в ней ≥ 120 значений из ≥ 3 суток;
3. иначе типовая норма с удвоенной σ — и показатель считается **«учится»**.

Типовая норма (med, σ): hr/rest 60, 10 · hr/sleep 52, 8 · spo2 97, 1.5 · rr 14, 3 · skin_t 33.5, 1.5.

Пока показатель «учится», уровни по z для него не выставляются — работают только жёсткие пороги.

### 6.4 z

`z = (x − med) / sig` — по норме из §6.3.

### 6.5 Пополнение буфера

Значение минуты попадает в буфер, если:

- показатель не `null`, контекст не `off`;
- **во время прогрева** (показатель «учится») — всегда;
- **после прогрева** — только при `|z| < 2.5` и отсутствии открытого инцидента у человека.

Факт попадания пишется в `agg_1m.learn_mask` (бит на показатель).

### 6.6 Восстановление при старте

Сервер читает `agg_1m` за последние 14 суток по каждому человеку и заполняет буферы по `learn_mask`. Никаких других таблиц для нормы нет.

### 6.7 Состояние обучения человека

- `days` = число разных суток с данными (не больше 7 для показа);
- `ready_pct` = готовые ячейки / ячейки, в которых есть хоть одно значение;
- `state = learned`, если `days ≥ 7` и `ready_pct ≥ 75`, иначе `learning`.

В момент перехода в `learned` создаётся системное уведомление `baseline_learned` (§7.6).

## 7. Уровни и инциденты

Уровни: 0 Usual · 1 Watch · 2 Alert · 3 Critical.

Отклонение от личной нормы (§7.1) даёт максимум Alert. Critical — только жёсткие пороги (§7.2) и среда (§7.3). Итог — больший из источников.

### 7.1 По личной норме

Для каждого показателя — счётчики подряд идущих минут. Пропуск минуты обнуляет счётчики.

| Уровень | Условие | Подряд |
|---|---|---|
| Watch | `|z| ≥ 2` | 5 минут |
| Alert | `|z| ≥ 3` | 3 минуты |

- `spo2` — только вниз (z отрицательный).
- В контексте `active` пульс и дыхание не оцениваются.
- В контексте `off` не оценивается ничего.
- Показатель «учится» → не оценивается.

### 7.2 Жёсткие пороги

Проверяются на каждой закрытой минуте, если `valid_s ≥ 40` (для типа 2 — всегда).

| Показатель | Alert | Critical |
|---|---|---|
| `spo2` | 92–93 | ≤ 91 |
| `hr`, контекст rest | 111–130 | ≥ 131 или ≤ 40 |
| `hr`, контекст sleep | 111–130 или ≤ 40 | ≥ 131 |
| `rr`, контекст rest/sleep | 21–24 | ≤ 8 или ≥ 25 |

### 7.3 Среда

| Показатель | Watch | Alert | Critical |
|---|---|---|---|
| `ppco2`, среднее за 60 минут (≥ 30 значений) | > 3.0 | > 5.3 | > 10.0 |
| давление | — | падение > 2 % за ≤ 10 минут | > 10 % ниже медианы за 24 часа |

### 7.4 Уровень человека и гистерезис

`raw` = максимум по §7.1–7.3 (и паттерну, §8.2).

- `raw > level` → `level = raw` сразу.
- `raw < level` 10 минут подряд → `level −= 1`, счётчик сбрасывается.

### 7.5 Инцидент

У человека не больше одного открытого инцидента.

| Событие | Действие |
|---|---|
| `level` стал > 0, инцидента нет | создать; `ts_start` = эта минута |
| инцидент открыт | обновлять раз в минуту: `level`, `peak_level`, список показателей, паттерн |
| `level` вернулся в 0 | закрыть: `ts_end` |
| `POST /alerts/{id}/ack` | `ack_ts`; уровень не меняется |

**Главный показатель** инцидента (для экрана Critical): тот, что сработал по жёсткому порогу; иначе — с наибольшим `|z|`.

Для каждого показателя в инциденте: `value`, `usual [lo, hi]`, `z`, `slope_per_min` (наклон за последние 10 минут), `since_min`, `trend` (`rising` / `falling` / `stable`).

**Тяжесть** 1–3 = `peak_level`.

### 7.6 Системные уведомления

Хранятся в той же таблице, `level = 0`, `source = 'system'`:

| `key` | Когда | Метка на фронте |
|---|---|---|
| `checkin:<дата>` | начались новые сутки, опрос не заполнен; закрывается при заполнении | To do |
| `baseline_learned` | §6.7 | Note |

На уровень и фон не влияют.

## 8. Паттерн

### 8.1 Модель

Раз в минуту на человека, когда есть ≥ 10 минут подряд. Признаки — `core/features.py` (40 штук, порядок из `pattern_meta.json`). Выход: класс и вероятность.

Классы: `normal`, `hypoxia`, `tachycardia_rest`, `bradycardia`, `fever_like`, `hypercapnia`, `depressurization`, `sensor_artifact`.

### 8.2 Использование

- Инцидент открыт → в него пишется `pattern`, `p` (если класс не `normal`).
- Инцидента нет, а класс не `normal` и не `sensor_artifact` с `p ≥ 0.8` три минуты подряд → `raw = 1` (Watch), источник `pattern`.
- `sensor_artifact` уровень **никогда** не поднимает.

### 8.3 Если модели нет

Файл не найден → паттерн по правилу от главного показателя:

| Главный показатель | Паттерн |
|---|---|
| `spo2` вниз | `hypoxia` |
| `hr` вверх, rest/sleep | `tachycardia_rest` |
| `hr` вниз | `bradycardia` |
| `skin_t` вверх | `fever_like` |
| `ppco2` | `hypercapnia` |
| давление | `depressurization` |

`p = null`. Этого достаточно, чтобы показать демо до готовности ML.

## 9. Текст инцидента

Три поля: `what`, `why`, `action` (английский).

**Шаг 1 — шаблон, синхронно.** Строится сразу при создании и при повышении уровня. Действия берутся из `actions.yaml` по `(pattern, severity)`. Инцидент уходит на фронт уже с текстом, `text_src = "template"`.

**Шаг 2 — LLM, в фоне.** `POST {OLLAMA_URL}/api/generate`, модель `vigil-narrator`, temperature 0.2, до 160 токенов, **таймаут 5 с**, одновременно не больше одного запроса. Ответ принимается, только если:

- ровно три строки с префиксами `WHAT:`, `WHY:`, `ACTION:`;
- каждое число в ответе есть во входной сводке.

Принят → текст заменяется, `text_src = "llm"`, фронту уходит обновление. Не принят, таймаут, Ollama недоступен → остаётся шаблон, в лог одна строка.

Для кадров с битом «повтор истории» шаг 2 не выполняется.

В тексте упоминаются только каналы, которые у этого устройства реально приходят: нет давления — фразы про давление нет ни в шаблоне, ни во входе LLM.

Вход для LLM — объект из `PLAN.md` §11.3 (паттерн, тяжесть, контекст, показатели, среда, симптомы из опроса, ключи действий).

## 10. База

```sql
create table crew (
  id        smallint primary key,
  name      text not null,
  role      text not null,
  dev_id    integer unique not null,
  share     jsonb not null default '{"sleep": true, "checkin": true}'
);

create table agg_1m (
  crew_id    smallint not null references crew,
  ts         timestamptz not null,           -- начало минуты
  hr real, spo2 real, rr real, skin_t real, hrv real,
  co2_ppm real, press_hpa real, amb_t real, ppco2 real,
  act_mg real, sqi real, worn_frac real, valid_s smallint,
  ctx        smallint not null,              -- 0 off, 1 sleep, 2 rest, 3 active
  z_hr real, z_spo2 real, z_rr real, z_skin_t real,
  lo_hr real, hi_hr real, lo_spo2 real, hi_spo2 real,
  lo_rr real, hi_rr real, lo_skin_t real, hi_skin_t real,
  level      smallint not null default 0,
  learn_mask smallint not null default 0,
  primary key (crew_id, ts)
);

create table alert (
  id         bigserial primary key,
  crew_id    smallint not null references crew,
  key        text not null,                  -- 'incident' | 'checkin:2026-11-14' | 'baseline_learned'
  source     text not null,                  -- baseline | hard | env | pattern | system
  ts_start   timestamptz not null,
  ts_update  timestamptz not null,
  ts_end     timestamptz,
  level      smallint not null,
  peak_level smallint not null,
  pattern    text, p real, ctx smallint,
  metrics    jsonb not null default '[]',
  text       jsonb,
  text_src   text,
  ack_ts     timestamptz
);
create index on alert (crew_id, ts_start desc);

create table checkin (
  crew_id smallint not null references crew,
  day date not null,
  sleep_q smallint, mood smallint, energy smallint,
  symptoms text[] not null default '{}',
  note text, filed_ts timestamptz not null,
  primary key (crew_id, day)
);

create table report (
  crew_id smallint not null references crew,
  day date not null,
  body jsonb not null,
  include jsonb not null,
  note text,
  queued_ts timestamptz,
  primary key (crew_id, day)
);

create table radiation_daily (
  day date primary key,
  dose real not null, unit text not null, instrument text not null
);
```

Коридор нормы (`lo_*`, `hi_*`) пишется в строку минуты, чтобы график за прошлое рисовался одним запросом, без пересчёта.

Запись `agg_1m`: в живом режиме — по строке; при повторе истории — пачками по 1000 через `copy_records_to_table`.

Объём: 7 человек × 1440 минут = 10 тыс. строк в сутки. Индексов, кроме первичных ключей, не нужно.

## 11. API

Все ответы — JSON. Времена — unix-секунды. `null` означает «нет данных» и никогда не заменяется нулём или прошлым значением.

### 11.1 Список

| Метод | Путь | Экран |
|---|---|---|
| WS | `/ingest` | — |
| WS | `/live?crew=1` | Today, метрика |
| GET | `/crew` | Crew |
| GET | `/crew/{id}/today` | Today |
| GET | `/crew/{id}/metric/{m}?range=1h\|24h\|7d` | метрика |
| GET | `/crew/{id}/alerts?open=1` | Notices |
| POST | `/alerts/{id}/ack` | Notices, Critical |
| GET, POST | `/crew/{id}/checkin` | Check-in |
| GET | `/crew/{id}/sleep` | Sleep |
| GET | `/crew/{id}/device` | Device |
| GET | `/crew/{id}/report/{day}` | Report |
| PUT | `/crew/{id}/report/{day}` | Report (галочки, заметка) |
| POST | `/crew/{id}/report/{day}/queue` | Report |
| GET | `/radiation` | Radiation |

     "usual": [95.0, 99.0], "limit": 91,
     "spark": [97, 96, 95, 93], "band": [95.0, 99.0]}
  ],

    {"m": "ppco2", "value": 2.6, "unit": "mmHg", "state": "usual", "limit": 3.0, "spark": []}

- `state` показателя: `usual` · `watch` · `alert` · `critical` · `learning` · `exercising` · `no_data` · `not_measured`. У каждой карточки состояние своё; оно не равно уровню человека.
- Если подходит несколько состояний, берётся первое: `not_measured` → `no_data` → `alert`/`critical` по жёсткому порогу → `exercising` → `learning` → `watch`/`alert` по личной норме → `usual`.
- `learning: true` — норма показателя ещё не выучена; тогда `usual` и `band` равны `null`. Сочетание `learning: true` и `state: "critical"` возможно (жёсткий порог сработал во время обучения).
  - `not_measured` — поле ни разу не приходило от этого устройства;
  - `no_data` — приходило, но сейчас `null`; добавляется `"since_ts"`;
  - `exercising` — контекст `active`, только для `hr` и `rr`.
- `spark` — 60 минутных значений за последний час, с `null` на месте пропусков.
- `notices` — открытые записи `alert` (инцидент и системные), формат §11.4.

## 12. Радиация

При старте: прочитать `data/radlab/*.json`, свернуть в суточные значения, записать в `radiation_daily`.

Даты в файле исторические. Сервер отдаёт последние 14 дней **из файла** и подписывает их днями файла; сдвигать даты под виртуальное «сегодня» нельзя — это подмена данных.

## 13. Устойчивость

| Ситуация | Поведение |
|---|---|
| Перезапуск сервера | норма восстановлена из `agg_1m`; открытый инцидент подхвачен из `alert`; счётчики подряд идущих минут начинаются заново |
| Нет файла модели | §8.3 |
| Ollama недоступен | шаблонные тексты |
| vdev недоступен | `/sim/*` отвечает 503; остальное работает |
| Битый кадр | отброшен, счётчик |
| Устройство замолчало | строки `agg_1m` не появляются; показатели на фронте — `no_data`; уровень снижается по гистерезису только при приходе новых минут, а пока — держится |
| Postgres недоступен при записи | минута остаётся в памяти, повтор через 1 с; приём не останавливается |

## 16. Тесты

Модульные (в `core/`, без сети и базы):

1. Кадр: туда-обратно; «нет данных» → `None`; битый CRC.
2. Минута: медиана; < 20 валидных секунд → `None`.
3. `ppco2`: 5000 ppm при 1013,25 гПа = 3,80.
4. Контекст: четыре случая из §5.3, включая 5 минут после нагрузки.
5. Норма: пример §6.2; ячейка не готова при 119 значениях; не готова при 500 значениях из 2 суток.
6. Пополнение: после прогрева значение с `|z| = 3` в буфер не попадает.
7. Уровни: 4 минуты `|z| ≥ 2` — Usual, 5 минут — Watch; пропуск минуты обнуляет счёт.
8. Гистерезис: вверх сразу; вниз через 10 минут и на одну ступень.
9. `sensor_off`: `worn = 0` → контекст `off`, уровень не растёт, инцидент не создаётся.
10. Нагрузка: пульс 140 при `active` → уровень 0.

Сквозной сценарий (скрипт против поднятого стенда):

1. `/sim/reset` → история 14 суток → у шести человек `baseline.state = learned`, открытых инцидентов нет.
2. Сценарий `hypoxia`, тяжесть 3 → уровень 3 не позже чем через 15 виртуальных минут; у инцидента `primary = spo2`, текст не пустой.
3. `ack` → `critical_acked = true`, уровень остаётся 3.
4. Конец сценария → уровень возвращается в 0, инцидент закрыт.
5. Сценарий `sensor_off` → показатели `no_data`, инцидента нет.
6. Перезапуск сервера → шаг 1 по-прежнему верен без повторной загрузки истории.
